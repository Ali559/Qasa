# Qasa browser extension

Manifest V3 extension for Chrome/Chromium/Edge and Firefox (plan:
[`docs/desktop-extension-plan.md`](../../docs/desktop-extension-plan.md) §8). It fills and
saves logins from the Qasa desktop app; it stores no vault data itself.

```
content script ⇄ service worker ⇄ (native messaging) nm-host ⇄ (unix socket / pipe) desktop app
```

## Layout

| Path | What |
| --- | --- |
| `src/shared/protocol.ts` | Wire protocol v1 (§8.2.1): pairing (ECDH P-256 + HKDF-SHA256), AES-256-GCM requests. Pure WebCrypto |
| `src/background/` | Service worker: the native port, pairing, request/reply matching, sender checks |
| `src/content/` | Field detection, in-page icon and menu (closed shadow root), clickjacking guard, fill, save capture |
| `src/popup/` | Vue popup, built from the desktop's components, tokens, fonts and i18n (`@` → `../desktop/src`) |
| `scripts/` | Build (three Vite builds → `dist/chrome`, `dist/firefox`), manifests, aliases, vector generator |
| `test/unit/` | Vitest: protocol + vector, bridge, field detection / save / fill (happy-dom) |
| `test/e2e/` | Playwright with the unpacked Chrome build, the real nm-host and `test/fake-desktop.ts` |
| `test/fixtures/` | Static pages for the e2e suite, served on `127.0.0.1` and `localhost` (two origins) |
| `test/vectors/bridge-pairing.json` | Cross-language pairing vector (the desktop's Rust test reads it) |

## Build

```sh
bun install
bun run build        # type-check, then dist/chrome and dist/firefox
bun run dev          # rebuild on change
make extension       # from the repo root: install + build
```

Strings come from `apps/desktop/src/i18n/*.json`, generated by `python3 l10n/generate.py`
from `l10n/strings.json` + `l10n/platform/desktop.json` (`ext.*` keys; `ext.page.*` are the
in-page menu's, the only ones bundled into the content script). The store name and
description are in `static/_locales/{en,ar}` (Chrome has no `ckb` locale).

## Load unpacked

- **Chrome / Edge:** `chrome://extensions` → Developer mode → Load unpacked → `dist/chrome`.
  The id is always `fiamcbmecfeeofaadngagmdldkgncmmd` (pinned by the manifest `key`, see
  [`EXTENSION_IDS.md`](EXTENSION_IDS.md)).
- **Firefox (128+):** `about:debugging#/runtime/this-firefox` → Load Temporary Add-on →
  `dist/firefox/manifest.json`. Id `extension@qasa-app.com`.

The desktop app installs the native host manifest (`com.qasa_app.desktop`) that lets the
extension reach it. For a dev build without the installer, write it by hand, for example on
macOS for Chrome, `~/Library/Application Support/Google/Chrome/NativeMessagingHosts/com.qasa_app.desktop.json`:

```json
{
  "name": "com.qasa_app.desktop",
  "description": "Qasa",
  "path": "/absolute/path/to/apps/desktop/nm-host/target/debug/qasa-nm-host",
  "type": "stdio",
  "allowed_origins": ["chrome-extension://fiamcbmecfeeofaadngagmdldkgncmmd/"]
}
```

(Firefox: `~/Library/Application Support/Mozilla/NativeMessagingHosts/`, with
`"allowed_extensions": ["extension@qasa-app.com"]` instead of `allowed_origins`.)

## Tests

```sh
bun run test         # Vitest: protocol, vector, bridge, detection, save, fill
bun run e2e          # build, then Playwright (Chromium, unpacked extension)
bun run lint:firefox # web-ext lint on dist/firefox
bun run vectors      # regenerate test/vectors/bridge-pairing.json (with Node's crypto)
```

The e2e suite needs the nm-host binary (`make nm-host`) and Playwright's Chromium 131
(`chromium-1148`, `bunx playwright install chromium` if missing). Each run makes a fresh
profile with a user-level host manifest in `<profile>/NativeMessagingHosts/`, starts
`test/fake-desktop.ts` on a temp unix socket and points nm-host at it with
`QASA_BRIDGE_SOCKET`. The in-page menu is in a closed shadow root, so tests click it by
coordinates from `src/content/layout.ts`, with real mouse events.

## Security rules

- **Stored:** only the pairing, `{clientId, key}`, in `storage.local` (plus the popup's
  language choice). No vault data, nothing cached: secrets in a reply go straight to the
  field and are dropped.
- **Trusted URL:** the URL sent with `matches`, `fill`, `totp` and `save` is always the
  browser's `sender.url` for the frame the content script runs in. The popup gets a tab's
  matches and fills through that tab's top-frame content script, so the same rule covers
  it; the popup never sends a URL.
- **Popup only:** `pair`, `copy`, `search` and `generate` are accepted only from our own
  extension pages; `matches`, `fill`, `totp` and `save` only from content scripts.
- **Frames:** each http(s) frame runs its own copy and handles only its own document, so a
  cross-origin frame can only get logins for its own origin. Frames without a URL
  (about:blank, srcdoc) are handled by their same-origin parent, with the parent's URL.
- **Never without a user action:** fills happen only after a trusted click on a menu row
  or the popup's Fill button. Nothing is filled on page load.
- **Clickjacking:** menu clicks must be `isTrusted`, at least 500 ms after the menu
  appeared, and land on our host (`elementFromPoint`). The host carries inline
  `all: initial … !important` styles; a page that rewrites them turns Qasa's UI off for that
  document. In Chrome, IntersectionObserver v2 must report the menu visible (catches covers
  with `pointer-events: none`). Before a fill, every target field must have a size, its
  centre in the viewport, be the topmost element at its centre, and have an opacity product
  of at least 0.5 with no hidden ancestor.
- **Save:** sent on submit, Enter or a submit-button click; never for an empty password or
  for a value Qasa just filled unchanged. The desktop asks the user before saving.
